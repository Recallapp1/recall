# Full audit of the Recall repository (2026-10-13)

_Hostile, evidence-based review of `main` at `5a91b97`. Owner-facing, in English like the other review documents. Docs, the decision log, WORKLOG, earlier audits and my own past summaries were treated as **claims**; evidence is code I read in this audit and commands I ran in this audit. Read-only for the application: the only files written are this report, [FULL-AUDIT-ACTION-PLAN.md](FULL-AUDIT-ACTION-PLAN.md), [AUDIT-PROGRESS.md](AUDIT-PROGRESS.md) and one link block in [NEXT-STEPS-FOR-OWNER.md](../NEXT-STEPS-FOR-OWNER.md). Throwaway probe tests ran from the git-ignored `outputs/audit-probe/` folder against the in-memory test database; nothing touched Neon, Vercel, Retell or GitHub settings, and no production network call was made._

## 1. Executive verdict

**Can a supervised pilot with real patients start once a phone line and Retell credit exist? Probably yes, with conditions.** The core flow (call → clinic → tool → booking → panel) is built, isolated per clinic, signed, rate-limited and heavily tested. Nothing found is a cross-clinic leak or an authentication bypass. But "probably" and not "yes", for five reasons:

1. **Two KVKK erasure gaps, both confirmed by execution, sit on the switch paths the pilot plan recommends.** Erasure leaves the family member's name in `appointments.booked_for_name` (`VOICE_SHARED_NUMBER_CHECK`, `PATIENTS_PER_NAME`), and after a phone correction (`PANEL_PATIENT_EDIT`) erasure and export miss every call from the old number (FA-01, FA-02). Both are small fixes; until they land, those switches should stay off.
2. **Nothing about real callers is proven.** The only measured data is 12 scripted web calls (2026-10-08): turn latency p50 ≈ 1.55 s against a 1.0 s target, and one call where the assistant claimed a booking it never made (prompt fixed since, not re-measured). Caller-ID format over SIP, Retell signing with the rotated key and behaviour on failure are all untested.
3. **Legal and commercial prerequisites are drafts.** No lawyer review, DPA, published notice, company or Vercel Pro (Hobby forbids commercial use). The baseline greeting does not say what [KVKK.md](../05-compliance/KVKK.md) says it says, and has no path for a caller who objects to recording (FA-04).
4. **Operations are thin for real patients.** No Sentry or uptime account, a 6-hour restore window that has never been drilled, clinic limits changeable only by a hand edit of the production database (FA-09), no clinic-offboarding deletion (FA-08), and a deploy path where the assistant's prompt is synced before the new code is live and is not rolled back with a Vercel rollback (FA-05).
5. **Docs overstate.** About 40 documents contradict the code in at least one place (section 6). The most important are compliance claims: "no `sql.raw`", "no `dangerouslySetInnerHTML`", erasure step lists, retention promises, "console cannot reach patient data" (FA-07, FA-16).

**Numbers (section 9):** code work done ≈ **82%**, pilot readiness ≈ **60%** (was stated as ~75%), general-sales readiness ≈ **35%** (was ~50%).

**Findings:** 0 critical, 2 high, 12 medium, 16 low (section 4). Every finding has `file:line` or is marked unverified.

**(1) Call → booking → SMS.** Retell `call_inbound` → `handleInbound` verifies the signature (`handlers.ts:63`, `:356-365`) → dialled number → clinic (`clinics.ts:37-44`) → agent row (`handlers.ts:74-87`) → admission limits (`voice-limits.ts:24-73`) → call row (`calls.ts:24-46`) → `override_agent_id` + variables (`handlers.ts:112-119`).
